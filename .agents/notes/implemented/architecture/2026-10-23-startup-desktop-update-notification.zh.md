# Agent Note: 桌面端启动更新发现与通知

Status: implemented

[English](2026-10-23-startup-desktop-update-notification.md) | 中文

## Problem

用户需要在不打开设置的情况下得知桌面端新版。版本发现必须在登录前可用，不延迟账号恢复，并保留发布认证与显式安装同意。

## Decision

[原生更新器](../../../../apps/electrobun/src/desktop-updates.ts)在每次应用启动时与账号恢复并行执行一次静默发现。只有签名有效、平台匹配且语义化版本更高的发布才生成可用版本记录。缺少配置、已是最新版、清单为空或发现失败时不显示进度或错误提示。启动发现不会下载安装包。

原生进程拥有本次启动的可用版本与关闭状态。[工作区 Client](../../../../packages/client/ui-enterprise/src/client/enterprise.tsx)通过 `shell.overlay` 渲染持续的悬浮通知；[账号页](../../../../packages/client/ui-enterprise-account/src/client/account.tsx)通过令牌保护的本地回环传输，在登录前提供相同操作。两者进入时以及收到可用性事件时均读取原生状态，因此导航和窗口替换会保留结果。关闭通知会清除跨窗口的原生状态。重启后可以再次发现；关闭通知后仍可手动检查。

“安装更新”进入已有的原生确认、验证下载和安装器交接流程。手动检查等待活动的启动发现，并共用一次手动交互。退出会中止发现、等待活动 I/O，并阻止迟到通知。账号更新分发不等待安装器完成，因为安装会停止同一个账号服务器；原生生命周期负责完成与错误处理。

此决策部分取代[签名桌面端更新决策](2026-10-20-signed-desktop-updates.zh.md)中仅手动发现的策略；该文仍保留独立的认证、密钥轮换和安装器交接依据。[Admin 发布](2026-10-21-admin-desktop-release-publication.zh.md)仍负责离线签名与不可变发布。

## Alternatives considered

**仅手动检查。** 不访问设置或原生菜单的用户无法及时发现发布。

**启动模态提示或自动下载。** 可关闭的通知让用户继续登录和工作，同时由用户明确决定安装包传输与任务停止。

**浏览器负责发现与轮询。** 单一原生发现让签名密钥、清单配置和发布验证留在既有所有者中，避免跨页面、跨窗口重复请求。每次启动都提供新的发现机会，无需后台轮询。

## Consequences

启动检查失败后，需要等下次启动或手动请求。关闭通知不是永久忽略该版本。通知中的安装操作会重新检查签名清单，因此可以显示启动后发布的更新版本。既有平台安装器确认和 macOS 手动替换保持不变。

针对性原生测试覆盖静默结果、每次启动一次的发现、签名拒绝、重叠手动请求与退出。Client 测试覆盖本地化通知输出、迟到读取、关闭、重试与释放。浏览器预期输出覆盖真实账号传输与工作区叠加层、窄屏布局、导航和安装分发。交互式操作系统安装仍需在对应平台验收。
