# Agent Note：工具可读图片与视频音轨能力

Status: implemented

[English](2026-09-17-tool-readable-images-and-video-audio-capability.md) | 中文

## 问题

模型原生模态描述提供方接受的内容块，但不能覆盖 agent 从附件获取信息的所有方式。在图片进入 Session 前就拒绝它，会让纯文本模型失去把已保存文件委托给 OCR、计算机视觉、MCP 或返回文本的代码工具的机会。

`video` 模态也不足以说明提供方只理解画面，还是同时理解画面与内嵌音轨。把内嵌音轨视为独立 `audio` 模态会混淆两种提供方保证，并使模型选择器夸大支持范围。

## 决策

图片附件准入不依赖所选模型的原生图片能力。附件服务负责校验并持久化图片，Session 在请求组装前记录其持久引用。原生图片路由接收图片块。明确不支持图片输入的路由则接收确定性文本；当附件与文件系统提供方都能暴露映射时，该文本包含规范化附件在当前执行环境中的只读路径。文本要求模型使用能够返回文字分析的可用工具；没有这种工具时必须报告限制。执行路径按请求解析，不写入 Session。

内置 `read_image` 工具仍只允许原生图片路由使用，因为它的结果包含图片块。路径句柄支持结果为文本的工具；它不会把纯文本模型变成视觉模型，也不表示部署中必然安装了这种工具。

视频、音频和文档附件采用同一个请求时恢复规则。具备原生能力的路由接收媒体块；缺少相应模态的路由接收包含当前只读执行路径的确定性文本，使可用的媒体、文件系统、代码或委派工具能够返回文字分析。没有可读路径时，文本要求模型报告限制。通用 `FileBlock` 记录与显式媒体块共享此行为。

模型元数据携带 `videoAudioMode: 'visual-only' | 'visual-and-audio'`。更强的 `visual-and-audio` 保证只有在路由输入模态包含 `video` 时才有效；企业元数据省略该字段时保守地解析为 `visual-only`，不支持视频输入的路由也采用这个默认值。两个值使用同一个提供方视频协议项。`visual-only` 路由保留原生视频块，并额外接收一个路径句柄，用于按需通过工具单独分析内嵌音轨。独立 `audio` 模态仍表示可以单独提交音频文件。

LLM 服务拥有这些提供方无关语义。提供方适配器报告精确路由元数据并序列化原生输入，Session controller 在模型目录中发布它，Admin 与 Client 界面负责配置和展示。agent loop 保持不变。

## 曾考虑的替代方案

**在提示词准入时拒绝纯文本路由的图片。** 这可以保证每个已接受图片都能原生发送，却会在模型能够选择工具之前移除工具分析机会，还会让附件持久化耦合到可变的模型选择。

**允许纯文本路由运行 `read_image`。** 它的成功结果是持久图片块，所以下一次请求仍需要原生图片输入。仅返回元数据则会声称执行了读图操作，却没有提供视觉分析。

**新增 `video-audio` 模态。** 内嵌音轨理解修改的是一次视频输入的保证，并不表示允许提交独立音频输入。单独模态会使协议投影和 UI 筛选产生歧义。

## 后果

原生与非原生媒体路由现在共享同一套失败关闭恢复策略。模型只能通过能够读取投影路径并返回文本的可用工具检查不受支持的图片、视频、音频或文档输入；否则它会收到明确的限制说明。模型目录和选择器可以区分只理解画面的视频与理解内嵌音轨的视频，而无需改变 OpenAI 或 Ark 的视频序列化。
