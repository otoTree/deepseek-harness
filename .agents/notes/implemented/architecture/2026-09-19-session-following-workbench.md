# Agent Note: Session-following Workbench separates UI ownership from capability state

Status: implemented

English | [中文](2026-09-19-session-following-workbench.zh.md)

## Problem

The desktop and Web clients need one Session-following details workbench while terminal, files, and browser capabilities keep their own Host-owned state and cleanup rules.

## Decision

`ui-workbench` is the sole owner of the layout `details` slot. Its session-scoped keyed child slot owns the Results, terminal, browser, and files panels, so switching Sessions remounts panel state without changing the three-column layout owner. Results reuses `ui-deliverables` Turn data and aggregates successful mutation paths across the loaded Chat timeline in first-seen order. The Results key props carry a file-open callback to Results; selecting a path changes the active tab, directory, and file selection in one Workbench store action, then the Files panel reads it through the bounded Workbench Remote. Chat uses the root-scoped Workbench file opener for turn-tail chips and message-body links, so those affordances open the same Session Files panel; compositions without Workbench retain the Host workspace opener as a fallback. Terminal operations continue to use `ctx.terminals`; file operations use `ctx.fs` with an expected version; browser state is an independent capability and does not change `ctx.web` search/fetch semantics.

The browser capability owns opaque context and tab identities and provider lifecycle. Host Controllers, model tools, and Client panels address the same Session-owned context. The desktop panel renders a sandboxed native Electrobun WebView, while the Web client renders an iframe; neither panel renders provider screenshots. The desktop keeps inactive native views hidden and input-transparent, and readiness events reconcile every view against the Client-selected tab before allowing pointer input. Every native view opened by one enterprise Runtime uses the same `persist:dsh-workbench-runtime-<runtimeStorageIdentity>` Electrobun partition across Sessions and Browser contexts. The desktop derives the non-secret storage identity from the deployment origin, organization id, and Runtime id; the identity contains no credential token, and another Runtime receives a separate partition. The active native WebView owns visible navigation, persistent storage, and history, and its `src` remains fixed after creation. Address submissions and toolbar commands act on that view; resulting navigation is mirrored to the Session Playwright page, and bounded native title, URL, navigation, and semantic DOM observations update Session browser state. Provider follow state cannot reload or navigate the native view. Model tools discover that context through `browser_tabs` and read the current native observation before falling back to the provider snapshot.

The native WebView and Playwright provider are separate browser engines. Native navigation and observations feed the provider mirror, while provider navigation does not drive native history. A direct native interaction is not an identical Playwright action. Desktop acceptance therefore verifies native rendering and interaction separately from provider automation and model-readable Session state.

The launcher contributes to `conversation.session.header.utilities` as an icon-only action, so users can open the Workbench from the session header after closing it. The terminal panel binds to a Session-owned persistent terminal and uses an xterm renderer. Keyboard bytes flow directly to the PTY, raw PTY output retains ANSI and cursor-control sequences, and renderer dimensions resize the provider. Bash owns line editing, history, completion, and foreground signals; model-facing sends continue to read a separate sanitized output view.

The files panel reads within the Session workspace through `ctx.fs`. Separate icons, colors, metadata, and accessible descriptions distinguish directories, regular files, and other entries. Valid UTF-8 files remain editable with expected-version replacement, while an allowlist maps common image, audio, video, and PDF filename extensions to browser-native media elements. A revocable Blob URL lets the browser's PDF viewer consume the bounded bytes without a sandboxed `data:` document. DOCX, PPTX, XLSX, and CSV bytes cross the Remote as bounded document payloads. XLSX parsing uses the browser ExcelJS bundle and renders one selected worksheet with named tabs, row and column headers, merged cells, stored dimensions, frozen panes, formatted values, and basic cell styles; visible cells are editable. DOCX exposes body paragraphs and table-cell text as editable fields. Saving DOCX or XLSX mutates only the addressed OOXML text or cell nodes and retains every other ZIP entry, then uses a version-guarded binary replacement. `ctx.fs.writeBytes` gives local, sandboxed, and E2B providers the same atomic publication, stale-version protection, and per-call sandbox policy as text writes without manufacturing text diff fields. The Workbench Controller accepts binary replacement only for canonical Base64 DOCX or XLSX ZIP payloads within its media limit. PPTX and CSV retain bounded read-only renderers; PDF and media remain browser-native read-only presentations. No preview executes macros, scripts, or embedded objects, and unrecognized binary files still fail closed. The enterprise desktop profile starts Sessions with `workspace-write`, which permits file replacement inside its organization workspace without granting paths outside that workspace.

Browser actions are automatically allowed at the product layer. URL protocol, tab count, observation size, resource size, and process cleanup limits are enforced by the current capability. Full browser-navigation SSRF resistance remains open implementation work; the current URL validation is not a DNS-pinned public-network policy.

## Alternatives considered

- **Keep `ui-chat` as the details owner** — it preserves the original composition, but every new panel would compete for the same layout slot and session switching would mix UI selection with capability state.
- **Render Playwright screenshots in the browser panel** — it would keep visible pixels and model actions in one engine, but pages would not reflow at the panel viewport and native browsing behaviors would be unavailable.
- **Claim that the native WebView and Playwright are one page** — it would hide their separate engine state and make interaction and acceptance claims misleading.

## Consequences

- Session changes remount panel content while preserving the surrounding three-column layout.
- The Results tab is the default Workbench tab and lists only successful mutation-tool paths from loaded Turns; terminal-created files remain outside this vocabulary.
- A Results selection opens inside Files without importing deliverables runtime code into Workbench; paths outside the Session workspace retain the file capability's rejection behavior.
- Browser, terminal, and file operations remain bounded by their existing providers and Remote contracts; the Workbench does not add a second capability registry.
- The native WebView shares cookies and site storage across native tabs, Sessions, and Browser contexts in one Runtime and preserves history across toolbar reloads; provider actions remain in the Agent mirror until native navigation updates it.
- Text reads and binary document payloads have separate configurable byte limits. DOCX and XLSX use an allowlisted binary replacement path; PDF, PPTX, CSV, media, and unrecognized binary content remain read-only and never become writable through the text mutation API.
- DOCX and XLSX saves retain untouched OOXML archive entries. The editors cover body text, table-cell text, and visible spreadsheet cell values, not full Office layout, formula calculation, macros, charts, or embedded-object editing.
- Direct terminal input bypasses the model-facing send reservation but remains owner-authorized and serialized at the backend; concurrent writers must coordinate their input.
- Desktop acceptance proves the native WebView's rendering and interaction; provider tests separately prove automation, observation storage, and model-readable page content.
- The details column can expand to 80% of the main content area while retaining a 240-pixel center floor; it closes when the details minimum and center floor cannot coexist.
- Browser URL checks enforce the current protocol and lifecycle limits only; deployments needing DNS-pinned public-network SSRF policy must add that policy before treating navigation as hardened.

## Verification

Client and Host TypeScript project references and focused Workbench/layout and browser/controller tests cover the dynamic details width, native WebView presentation, stable view attachment, Runtime-scoped persistent storage, inactive-view pointer isolation, observation limits, observation invalidation, provider fallback, version-checked text editing, media-type selection, media byte limits, and browser-native image, audio, video, and PDF presentation. The Files panel test additionally covers Blob URL release, a generated two-worksheet XLSX with named tab switching, row and column headers, merged cells, stored dimensions, formatted numbers, frozen panes, and basic styles, and a workbook whose embedded image uses an absolute drawing target while a non-drawing relationship and cell content remain readable. The focused native browser test also proves that Sessions and Browser contexts in one Runtime receive the same persistent partition, a different Runtime receives another partition, provider URL changes cannot replace an attached WebView source, desktop address submission waits for native navigation before mirroring it, native history or reload controls never invoke the Playwright provider, and a late readiness event cannot reactivate an inactive view. The rebuilt enterprise desktop bundle starts with the updated client, and the documentation quick and full synchronization gates pass. An automated real-model Web acceptance opened and read the httpbin form through the Session Playwright provider, rendered it in the live iframe, resized the Workbench from 359 to 1,106 pixels (79.9% of the main content area), and edited a form control without submitting it; this validates the Web fallback, not the native WebView. An authenticated enterprise desktop acceptance opened the Workbench from the Session header and exercised the xterm-backed shell with direct command input, ArrowUp history, Tab completion, and Ctrl-C interruption. A same-Runtime browser recording expanded the Workbench to 1,311 pixels, rendered ANSI green output, and repeated the history, completion, and interruption path; it validates the shared enterprise Runtime and Web renderer, not the native browser WebView. Authenticated manual acceptance remains required for native browser page interaction, viewport reflow, navigation synchronization, and model-readable semantic content.

Four focused test files pass 120 tests, the repository TypeScript check passes, the Workbench bundle builds, and the documentation quick check passes. The enterprise desktop command rebuilds the production client and starts its API, Admin, renderer, and Electrobun process. Round-trip acceptance with an existing five-worksheet XLSX and a nine-page DOCX reopens the edited values, preserves every ZIP entry, and changes only the selected worksheet XML or `word/document.xml`; LibreOffice opens and exports both saved files, and the original and edited DOCX exports retain the same page count and layout. The bundled LibreOffice renderer lacks some Chinese fonts, so both the original and edited DOCX exports show the same missing-glyph boxes. Direct Office editing in the native window remains a manual acceptance item because the test automation bridge cannot control Electrobun's native surface.
