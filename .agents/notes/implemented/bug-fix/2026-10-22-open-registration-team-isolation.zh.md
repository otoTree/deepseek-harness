# Agent Note: 开放注册隔离团队组织

Status: implemented

[English](2026-10-22-open-registration-team-isolation.md) | 中文

## Problem

挂在平台根组织下的团队可能沿公司层级继承平台成员身份和角色。仅依赖 RLS 的通讯录查询也可能暴露祖先组织成员；API 使用绕过 RLS 的凭据时，还可能暴露所有组织成员。允许注册不代表用户同意加入其他组织。

## Decision

开放部署创建独立团队根组织。只有私有公司部署的成员查找、固定角色、自定义权限和成员/角色 RLS 策略才遍历祖先组织。迁移 `0038_open_team_isolation` 将该规则应用于已有组织关联，不改变显式成员关系，也不移动客户数据。平台管理员使用控制面路由；仅有平台根组织的成员身份不会获得客户团队权限。

账户概览、订阅、设备、通讯录成员、角色绑定、部门分配、待接受邀请和成员用量都显式选择当前组织。席位限额只统计该组织。设备授权和撤销同时要求设备 ID 与组织 ID 匹配；授权返回该组织的策略版本。登录授权不设设备限额。接受邀请读取受邀组织的订阅和根部门。成员状态变更、角色撤销和邀请撤销也选择当前组织；最后一名 Owner 检查只统计该组织的 Owner。停用成员身份只撤销该团队的 Runtime。

[身份提案](../../proposed/architecture/2026-09-05-enterprise-identity-and-organization.zh.md) 继续负责整体账号与组织模型。本决策明确其中的开放团队隔离规则；提案因其独立的未完成能力而保持有效。[部署凭据决策](../architecture/2026-10-21-enterprise-single-database-connection.zh.md) 继续说明特权数据库账号绕过 RLS 的风险；通讯录的显式过滤不意味着此类凭据在整个应用中都安全。

## Alternatives considered

**只过滤展示的成员。** 这会掩盖通讯录症状，而继承的成员身份和角色仍然允许访问团队 API。

**只依赖 RLS。** 私有公司需要祖先组织可见性，受支持的部署凭据又可能绕过 RLS。组织本地的通讯录过滤仍然必要。

**全面删除层级继承。** 私有公司需要共享组织层级。部署模式独立于账号注册策略决定继承行为。

## Consequences

已有显式成员关系继续有效；服务无法推断哪些关系出于用户本意。开放部署中已有组织关联继续供平台管理使用，但不授予客户团队权限。[HTTP 回归测试](../../../../apps/api/tests/team-isolation.test.ts) 升级已有层级，覆盖普通和超级用户数据库账号、跨团队拒绝、最后一名 Owner 保护、独立注册团队、账户与订阅身份、设备注册、跨团队设备拒绝、邀请席位准入和私有公司继承。[Web 场景](../../../../snapshots/web/enterprise-settings/snapshot.yml) 在团队通讯录中展示团队 Owner。
