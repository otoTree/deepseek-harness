# Agent Note: 企业身份与组织模型

Status: proposed

[English](2026-09-05-enterprise-identity-and-organization.md) | 中文

## 问题

商业平台需要同时支持个人注册、企业部门、分公司、团队、计费和私有化部署，且不能维护两套用户与租户模型。若会话、插件、用量或权限直接挂在用户上，数据归属和委派管理会变得含混，open 与 private 版本也会逐渐分叉。

## 提议

- `Account` 表示人员或服务身份。所有业务操作都必须处于 `Organization` 上下文，并记录不透明的 `organization_id`。
- 个人空间表示为仅有一个成员的 `Organization(kind: team)`，不另建 workspace 表；使用同一套订阅和额度机制。
- 用 `Membership` 连接身份，用 `RoleBinding` 在组织或 `OrgUnit` 作用域绑定角色。部门、分公司、团队、项目和成本中心统一建模为可扩展的 `OrgUnit` 树。
- `Subscription` 绑定 Organization。服务端计算权益并控制席位、模型用量、运行时、插件、存储和限制；客户端不能自行授予权限。
- 浏览器和桌面安装以 `RuntimeInstallation` 标识，在组织下完成注册、心跳、策略刷新和撤销。
- `open` 部署允许注册时创建团队或接受邀请；`private` 部署预置唯一企业 Organization 并关闭公开创建组织。两种模式共享记录和协议，仅策略不同。
- 每个请求都必须解析已认证 Account、所选 Organization、成员关系、角色作用域、订阅和运行时策略，然后才授权与计量。

## 实现证据

[企业 API](../../../../apps/api/README.zh.md) 实现了初步的 Better Auth 与 PostgreSQL 组织模型。事务内组织选择和强制 RLS 隔离业务表，运行账号无法绕过 RLS。成员变更锁定组织，检查席位限制并保护最后一名不同的有效 Owner。部门作用域绑定可以保存，但部门委派尚未实现。

[数据库测试](../../../../apps/api/tests/identity.test.ts) 覆盖跨租户拒绝、并发席位准入、邀请重放与撤销、重复 Owner 绑定、管理员读取正文审计、单次 PKCE 授权码、运行时撤销及仅追加会话租约。构建产物测试通过命名 DSH profile 在操作系统分配的回环端口启动，并等待关闭完成。这些证据不能证明桌面功能对齐或真实模型提供方行为正确。

本提案继续保留，因为原生客户端、远程 DSH 提供方、委派角色计算及完整商业权益机制尚未完成。[平台提案](2026-09-05-enterprise-agent-platform.zh.md) 继续负责执行位置与插件治理，两份提案均未被完全取代或归档。

## 备选方案

- 个人用户与企业用户两套数据表：放弃，迁移、权限、计费和功能会分叉。
- 在 `user` 上保存 `company_id` 或 `department_id`：放弃，用户可属于多个组织单元，且作用域角色需要委派与历史记录。
- 私有化另建身份实现：放弃，会产生不兼容的部署行为和升级路径。
- 由客户端决定组织和权限：放弃，遭篡改或过期的客户端可能绕过服务端策略。
- 独立的 `PersonalWorkspace` 实体：放弃，单成员团队 Organization 能以更少概念提供相同产品行为。

## 验收条件

- 新注册 Account 在使用业务功能前，必须加入已有 Organization 或创建 team Organization。
- 个人团队、企业组织和私有化部署使用相同的会话、插件、用量、审计和计费记录。
- Organization 支持嵌套 OrgUnit，以及多个带作用域的角色绑定。
- 当组织上下文、成员关系、权益、运行时注册或策略版本缺失或撤销时，服务端请求默认拒绝。
- 组织转移、成员移除、保留、导出和删除保持审计能力，不遗留计费或安全相关记录。

## 风险

组织树和作用域角色会增加授权复杂度，需要集中策略计算和默认拒绝测试。账户发现与邀请可能泄露成员信息，应减少枚举并要求地址验证。私有化版本可能落后 SaaS 的架构版本，应共享迁移与兼容性测试。单成员团队在界面上可能被误认为个人账户，应明确显示组织类型，同时保持存储模型统一。
