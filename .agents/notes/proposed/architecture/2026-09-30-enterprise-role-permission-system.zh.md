# Agent Note: 管理端与桌面执行的企业角色权限

Status: proposed

[English](2026-09-30-enterprise-role-permission-system.md) | 中文

## 问题

企业产品已经包含平台管理、组织管理、桌面 Runtime 身份、插件激活和本机沙箱审批，但这些机制尚未形成一套明确的授权模型。现有路由混用平台标记、固定角色列表和权限检查。宽泛角色可能被误认为设备权限，本机批准可能被误认为企业权限，策略变更也尚未一致地使 Runtime 视图失效。产品还需要为高风险操作提供可选的职责分离，同时避免每个普通操作都等待另一名管理员。

## 提议

使用两个相互独立的企业权限平面和一个本机同意平面。平台角色治理部署级资源，但不能访问客户会话内容。组织角色通过稳定权限 ID 和带作用域的绑定治理租户资源。桌面用户独立控制本机文件、Shell、沙箱模式和逐次工具审批；跨越企业资源与本机资源的操作需要同时获得两侧决定。

Organization 拥有组织策略。组织管理员可以通过企业 API 在桌面客户端或 Web 管理后台管理同一套策略。桌面端是成员加入和日常治理的便捷入口，提供有效角色说明、策略草稿、影响预览和变更确认。复杂角色设计、身份提供商、计费、组织范围数据规则和批量变更优先使用 Web 后台；平台区域保持独立且仅在 Web 提供。两个组织管理入口使用相同的 API 和授权决定。在控制台中选择某个 Organization 不会使平台运维人员自动成为其成员或管理员。客户内容支持访问需要另行取得客户批准、限定范围和时间的授权。

系统角色和自定义角色使用相同的版本化角色定义及权限绑定。角色绑定到平台、Organization 或 OrgUnit 作用域。Organization 和 OrgUnit 绑定向下继承，任一适用的显式 deny 都覆盖普通 allow。最后 Owner 恢复、非升权、租户归属和平台职责隔离属于角色和 deny 都不能移除的系统约束。

所有受保护 API 操作使用同一个服务端解析器。它认证主体，验证账号、成员关系、Runtime、服务和插件状态有效，应用系统约束，展开带作用域角色，应用 deny 优先，检查权益，判断是否需要审批，并校验已提供策略修订。客户端可以使用有效决定视图改善展示，但绝不能把它作为授权提交。

允许每个 Organization 针对选定的高风险权限和作用域启用双人审批。申请人必须已经拥有权限。另一名有权审批者针对一个策略修订下的确切操作摘要在有限期限内批准。执行时重新验证申请人，并在受保护变更的事务中只消费一次批准。批准不能产生缺失的 RBAC 权限。

组织默认策略遵循最小权限：邀请会过期且只创建 Member；有效 Member 可在套餐限额内使用已批准模型、安装已批准的个人插件。会话内容仅所有者可见，跨成员读取、组织范围搜索和导出默认拒绝。组织插件安装、发布、审批、自定义权限授予、身份提供商变更、计费修改和设备范围策略变更需要明确权限；读取审计和计费记录也需要明确授权。策略设置可以限制操作或要求工作流，但不会增加角色权限或放宽平台上限。角色模板是细粒度读取、修改、使用、发布、导出、批准、撤销和删除权限的入门组合，不替代逐操作检查。

桌面离线时，用户授权的本机工作可以继续。企业模型、组织数据、云插件和管理操作需要当前在线授权，并在离线时默认拒绝。

## 现有基础

企业 API 已经存储 Organization、成员关系、OrgUnit、固定角色绑定、权限目录、版本化自定义角色、自定义角色权限以及 allow 或 deny 效果。它还提供 RLS 租户隔离、最后 Owner 检查、Runtime 租约与撤销、心跳和模型请求策略修订、插件权限修订及审计记录。[企业管理平台基础能力](../../implemented/architecture/2026-09-30-enterprise-admin-foundations.zh.md)继续负责这些已交付记录和接口。

[身份与组织提案](2026-09-05-enterprise-identity-and-organization.zh.md)负责账号、成员关系、Organization、OrgUnit、订阅和 Runtime 身份。本提案细化适用于这些实体且尚未解决的授权规则。[企业角色权限体系](../../../../docs/developer/discussion/enterprise-role-permission-system.zh.md)记录完整目标和迁移方式。

## 备选方案

**在平台、组织和桌面之间使用一套通用角色层级。** 放弃，因为平台操作、租户数据和操作系统访问拥有不同权威方。合并它们会使控制平面授权被误读为本机同意，或使平台支持权限暴露客户内容。

**由管理员控制桌面沙箱和本机审批。** 放弃，因为设备操作者仍然对本机文件、Shell、原生应用和操作系统提示负责。企业策略可以拒绝企业服务操作，但不能授予或绕过本机访问。

**只使用可继承的 allow 角色。** 放弃，因为委派管理需要在不复制所有父级角色的情况下排除少量权限。显式 deny 在所有适用绑定之间采用简单的全局优先规则，系统恢复约束负责避免 deny 导致无法恢复。

**只使用固定角色。** 放弃，因为客户需要以不同方式拆分身份、安全、插件、财务和会话职责。稳定权限 ID 和自定义角色可以满足该需求，而无需为每条路由增加产品特有角色名。

**所有高风险操作都强制双人审批。** 放弃，因为团队部署和私有化部署的人员配置及风险要求不同。审批默认关闭，由策略针对选定权限和作用域启用。

**把批准视为临时权限。** 放弃，因为批准不能提升缺少当前 RBAC 权限的申请人。它只确认一个摘要、修订和有效期均未变化且本来已获授权的操作。

## 验收条件

- 平台角色和组织角色在独立平面中解析，平台权限绝不授予客户会话内容访问。
- Organization Owner 可以从桌面端或 Web 后台通过同一组织 API 管理组织策略；平台运维人员不能仅凭控制台导航获得组织权限。
- 成员、角色、身份、Runtime、会话、模型、插件、用量、计费、审计和审批操作拥有独立的最小权限 ID。
- 新成员获得 Member 权限；会话导出、广泛会话读取、管理策略变更、计费变更和身份变更在明确授权前均拒绝。
- Organization 和 OrgUnit 绑定向下继承；适用 deny 覆盖 allow；最后 Owner 始终可以恢复。
- 系统角色和自定义角色通过稳定权限定义解析，自定义角色不能包含平台权限或本机同意权限。
- Runtime、服务账号和插件凭据只能收窄所属主体的当前权限。
- 每条受保护 API 路由都使用集中解析器，并与操作一起提交所需审计数据。
- 每次影响授权的变更都会推进相应策略修订，陈旧 Runtime 请求在执行前失败。
- 可选审批拒绝自我审批、重放、过期、载荷或修订不符以及申请人权限变化。
- 桌面离线行为保留由用户授权的本机工作，并拒绝企业服务操作。
- 定向集成测试覆盖跨租户拒绝、继承、deny 优先、撤销、陈旧策略、本机与企业权限交集以及批准消费。

## 风险

全局 deny 优先容易解释，但可能使期望子级 allow 覆盖父级 deny 的管理员感到意外；有效决定解释必须显示产生拒绝的绑定和作用域。集中解析器成为安全关键组件，需要针对每种资源所有者和列表路径进行事务级测试。策略修订失效可能中断合法工作，因此客户端需要明确的刷新和重试行为，且不能提供陈旧策略绕过。可选审批增加持久状态与并发风险；申请创建、决定、消费、变更和审计都需要明确的幂等性与归属规则。
